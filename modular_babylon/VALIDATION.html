Remote lobby/world routing (2026-11-18)

The reported failed join was a destination error: a separate Windows DreamSeeker reached the Linux host's lobby over the LAN, but the supervisor's default public_host=127.0.0.1 sent it to its own machine for the child connection. The original child reached ready, remained alive and saved/stopped normally; there was no admission. The quoted restart message came from the stale lobby browser's 15-second heartbeat watchdog after the intentional disconnect.

modular_babylon/connection.dm, included by the lobby and both game builds, validates destinations and routes default loopback links through the server IP:port returned by BYOND's winget(client, null, "url"). It preserves the configured target port and ticket query. Non-loopback public addresses remain authoritative. Invalid endpoints fail closed. This uses the connected server address, never client.address (the player's address). BYOND documents the special call in https://www.byond.com/docs/ref/skinparams.html.

  • Lobby join_world: ordinary Join/Create, tutorial Play/Edit, admin spectating and the existing rejoin flow all use this common handoff. Tutorial copies use ordinary Join from My worlds.

  • Lobby: the browser document's load event now sends a generation-tagged readiness notification. It bypasses page actions and their busy state, checks ownership, page initialization and the current connection's generation, then waits for mainwindow visibility.   • Both Babylon and station game builds share code/interface.dm: the existing visible-window callback now has a per-client guard and requests top-level focus after its maximize/viewport setup. A saved fullscreen preference still skips maximization. Resize only schedules viewport fitting.

Native API evidence and limits:

  • BYOND skin parameters documents focus=true for all controls (including MAIN windows), is-maximized=true for MAIN, and is-default as selection of default controls. Maximization is a separate, preceding write; no new automatic fullscreen setting is issued.
  • This is the supported native activation request. The reference does not guarantee that a background DreamSeeker will appear above another application. The request is consumed once even if activation is denied. There are no new OS utilities, reconnect workarounds or focus retries.
